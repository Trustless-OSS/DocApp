# Contributing

Thank you for your interest in contributing to Trustless OSS! We're a community-driven project and welcome contributions of all kinds.

## Ways to Contribute

### Code Contributions
- **Bug fixes**: Help us squash bugs
- **Feature development**: Build new features for the platform
- **Documentation**: Improve our docs and guides
- **Tests**: Add test coverage

### Non-code Contributions
- **Bug reports**: File issues with clear reproduction steps
- **Feature requests**: Suggest new features or improvements
- **Code review**: Review pull requests from other contributors
- **Community support**: Help others in discussions and forums

## Getting Started

### Prerequisites
- Git installed
- Node.js 18+ and pnpm
- Basic understanding of TypeScript
- GitHub account

### Development Setup

1. **Fork the repository**
   ```bash
   git clone https://github.com/Trustless-OSS/trustless-oss.git
   cd trustless-oss
   ```

2. **Install dependencies**
   ```bash
   pnpm install
   ```

3. **Set up environment variables**
   ```bash
   cp .env.example .env.local
   # Edit .env.local with your configuration
   ```

4. **Start development server**
   ```bash
   pnpm dev
   ```

5. **Run tests**
   ```bash
   pnpm test
   ```

## Development Workflow

### 1. Find an Issue

Check our [GitHub Issues](https://github.com/Trustless-OSS/trustless-oss/issues) for:
- Issues labeled `good-first-issue`
- Issues labeled `help-wanted`
- Issues with bounties attached

### 2. Claim an Issue

Comment on the issue to let us know you're working on it. This helps prevent duplicate work.

### 3. Create a Branch

```bash
git checkout -b feature/your-feature-name
# or
git checkout -b fix/issue-number-description
```

### 4. Make Changes

Follow our coding standards:

- **TypeScript**: Strict mode enabled
- **Formatting**: Use Prettier (configured in project)
- **Linting**: ESLint rules enforced
- **Commits**: Conventional commits format

### 5. Write Tests

Add tests for your changes:
```typescript
// Example test
describe('BountyService', () => {
  it('should create a new bounty', async () => {
    const bounty = await createBounty(params);
    expect(bounty.id).toBeDefined();
    expect(bounty.status).toBe('active');
  });
});
```

### 6. Update Documentation

If your changes affect:
- **API**: Update API documentation
- **Features**: Update feature documentation
- **Configuration**: Update configuration guides

### 7. Submit Pull Request

Create a PR with:
- Clear title and description
- Link to related issue
- Summary of changes
- Screenshots (if UI changes)

## Coding Standards

### TypeScript

```typescript
// Use explicit types
function createBounty(params: CreateBountyParams): Promise<Bounty> {
  // ...
}

// Use interfaces for object shapes
interface Bounty {
  id: string;
  amount: string;
  currency: Currency;
  status: BountyStatus;
}

// Avoid `any` type
// Bad: const data: any = response;
// Good: const data: ApiResponse = await response.json();
```

### React Components

```tsx
// Use functional components with TypeScript
const BountyCard: React.FC<BountyCardProps> = ({ bounty, onClaim }) => {
  // Component logic
  return (
    <div className="bounty-card">
      <h3>{bounty.title}</h3>
      <p>${bounty.amount} {bounty.currency}</p>
      <button onClick={onClaim}>Claim Bounty</button>
    </div>
  );
};
```

### Error Handling

```typescript
// Use try/catch with specific error types
try {
  await fundBounty(bountyId, amount);
} catch (error) {
  if (error instanceof StellarError) {
    handleStellarError(error);
  } else if (error instanceof NetworkError) {
    handleNetworkError(error);
  } else {
    handleUnknownError(error);
  }
}
```

## Pull Request Process

### Review Criteria

Your PR will be reviewed based on:

1. **Functionality**: Does it work as intended?
2. **Code quality**: Is the code clean and maintainable?
3. **Tests**: Are there adequate tests?
4. **Documentation**: Is documentation updated?
5. **Performance**: Does it impact performance negatively?

### Review Process

1. **Automated checks** (CI/CD pipelines)
   - Tests pass
   - Linting passes
   - Build succeeds
   - Code coverage maintained

2. **Maintainer review**
   - Code review by core maintainers
   - Design review (if applicable)
   - Security review

3. **Merge approval**
   - Requires at least 1 approval
   - All checks must pass
   - No outstanding review comments

## Release Process

### Versioning

We use [Semantic Versioning](https://semver.org/):
- **Major**: Breaking changes
- **Minor**: New features (backwards compatible)
- **Patch**: Bug fixes

### Release Schedule

- **Patch releases**: Weekly (as needed)
- **Minor releases**: Monthly
- **Major releases**: Quarterly

### Release Checklist

- [ ] All tests pass
- [ ] Documentation updated
- [ ] Changelog updated
- [ ] Version bumped
- [ ] Release notes written
- [ ] Announcement prepared
